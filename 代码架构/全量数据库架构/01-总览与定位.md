## 章 1 · 执行摘要

### 1.1 一句话

**全量市场数据库（MD-Foundation）是一台"自我维护的数据机器"**：每日盘后自动补齐缺口、把九万余个年度分区文件维持在可被任意消费侧独立复算的状态，并通过断点、体检、回归三层机制保证"**入库的数据可被证明是对的那一份**"。

### 1.2 现状（as-is，已服役）

| 维度 | 现状 |
|---|---|
| 形态 | 单机 Parquet 数据湖，**目录即分区**：`by_year` 70 / `single` 38 / `mixed` 4 / `by_code` 1（113 目录 / 10,852 文件 / 7,366 MB / **2.914 亿行**） |
| 主链路 | 每日 17:30 `gap-update --group all`（core 7 + extend 34）→ `alt-update` → `fund-nav` → 派生 → 日报/推送 |
| 采集引擎 | `fetch/backfill.py` 8 种取数模式 + `common/parquet_store.py` 落盘器；断点三态（成功/部分/失败）+ 磁盘双校验 |
| 读取契约 | 维护层 `common/reader.py`（纯本地 fail-fast）与决策层 `赤潮/market_data.py`（线上/本地双分支可降级）**分层不合并** |
| 可信机制 | `regress` 16 断言组/28 检查项；`db-audit` 断点/重复/缺口/规模四类体检；`ckpt` 交叉核对；`freshness` 新鲜度速查 |
| 已知短板 | ① 无快照即时回滚（历史版本不可重现）② 依赖单一 API 授权档（7 个漏网接口随时可能失效）③ 派生层与主干同库同盘（写风险耦合）④ 无并发写锁（单进程假设）⑤ 数据字典靠文档维护而非机读真源 |

### 1.3 目标态（to-be，建议）

四条收敛方向（详见 03/11/12 号）：

1. **契约化**：表规格、校验规则、新鲜度阈值统一进 `config.py` 单一真源，文档从真源**生成**而非手写。
2. **分层硬化**：主干（raw/normalized）与派生（derived）、服务（serving）在**目录权限与写通道**上分层隔离，派生重算不触碰主干。
3. **可回溯**：关键表引入"日/周快照 + 变更留痕"，使任一时点的库状态可在 [假设] 分钟级内重建（PoC-2）。
4. **可观测**：把体检从"人工跑命令"升级为"每日自动打分 + 异常推送"，用 6 项库级 SLO 量化（14 号 §22）。

### 1.4 结论（供决策者只看三行）

- 现有架构**方向正确**（Parquet + 目录分区 + 单真源 + 断言守卫），不需要推倒重来；需要的是**契约化、分层硬化、可回溯、可观测**四项增量。
- 最紧迫的两个风险：**漏网接口失效**（单点依赖）与**无快照回滚**（误覆盖不可逆）。
- MVP 增量建议只做三件事：K1 表规格机读真源、K2 快照与回滚、K3 库级 SLO 看板（见 11 号 §16）。

## 章 2 · 目标、非目标与范围

### 2.1 目标（可验收）

| # | 目标 | 验收判据（可机检） |
|---|---|---|
| G1 | **完整性**：登记在册的表全部按规格存在且覆盖连续 | `db-audit` 缺口 0（允许表级豁免清单显式例外）+ `regress` R 系断言全绿 |
| G2 | **新鲜度**：核心表在每交易日 17:30 流水线后达到 T 日 | `freshness` 输出 core 7 表 `max_date == 最近交易日` |
| G3 | **幂等性**：同一批数据重复执行结果不变 | 重复跑 `gap-update` 后行数与内容摘要（`metrics_digest` 式对比）零差异 |
| G4 | **可追溯**：任一张表可回答"该行来自哪个接口、哪次运行、断点状态" | 断点 + 日志 + 行数三方一致（`ckpt --verify`） |
| G5 | **布局一致**：任何表只存在一种布局，且与 `table_storage_layout()` 判定一致 | `reader.inspect_layout()` 无"混合布局"告警 |
| G6 | **只读隔离**：消费侧与回测侧无法写主干 | 代码级守卫（路径白名单）+ 抽查写调用为 0 |
| G7 | **可消费性**：消费侧不依赖目录/文件名细节 | 消费侧代码中 `glob(dir/*.parquet)` 命中数为 0 |
| G8 | **可恢复**：任一表可从冷备 + 重拉在可接受时间内重建 | PoC-2 实测（目标：单表 ≤ 30 min，全库 ≤ 24 h）[待验证] |

### 2.2 非目标（明确不做）

| # | 非目标 | 理由 |
|---|---|---|
| N1 | 分钟级 K 线与 Level2 盘口入库 | 走网页直连通道，量级与授权均不匹配（`全量数据库说明 §六.9`） |
| N2 | 引入 OLTP/列存数据库引擎（PostgreSQL/DuckDB 服务化/ClickHouse） | MVP 无并发写入与在线服务压力，收益不抵迁移风险（ADR-1） |
| N3 | 云端/多机分布式存储与计算 | 单机 7.4 GB 级规模、日增 < 30 MB；分布式成本远大于收益 |
| N4 | 实时流式采集与推送 | 日线为主的决策节奏，分钟级需求由盘中网页通道满足 |
| N5 | 付费接口档位升级以消除漏网依赖 | 成本与收益不匹配；改为"监控 + 可降级"策略（ADR-8） |
| N6 | 库内计算决策指标（信号、因子） | 派生层可承载，但**主干只存观测值**，不做策略语义（ADR-4） |
| N7 | 统一两套读取层 | 口径差异是有意设计，合并会破坏降级能力（`数据读取层分工.md §已知边界`） |
| N8 | 数据授权转售/对外分发 | 授权条款限制（10 号 §15.4） |

### 2.3 范围矩阵

| 数据域 | 现状承载 | 是否主干 | MVP 取舍 |

## 章 3 · 利益相关者与典型场景

### 3.1 利益相关者与关注点

| 角色 | 关注点 | 对库的"接口" |
|---|---|---|
| 库维护者（本人/自动化） | 日更是否成功、断点是否可信、失败能否续跑 | `gap-update`/`ckpt`/`db-audit`/`freshness` |

| 数据源管理员 | 权限档、限额、漏网接口、替代源 | 权限总账 + `doctor`/`config-check` |
| 审计/验收方 | 事实是否可复核、结论是否有证据 | 本文档 + `db-schema` 机读导出 |

## 章 4 · 质量属性与约束

### 4.1 质量属性（含现状与目标）

| 属性 | 现状实测/事实 | 目标（MVP 后） | 度量手段 |
|---|---|---|---|
| **可靠性** | 日更 17:30 automation 在跑；失败表级告警（PushPlus） | 连续 30 交易日 core 7 零失败 | `freshness` + 告警日志 |
| **一致性** | 断点与磁盘双校验；`ckpt` 交叉核对 | 断点-磁盘差异 0（除显式复核窗口） | `ckpt --verify` |
| **完整性** | `db-audit` 四类体检可跑；已有 X 档 6 张 disabled（死结）显式登记 | 缺口 0（豁免表除外） | `db-audit` 报告 |
| **幂等性** | 复核窗口重拉最近 3 交易日；无参快照表排除 | 重复执行内容摘要零差异 | R 系断言 + 摘要比对 |
| **性能** | 按年大表后 `moneyflow` 由 1 天/分钟 → **41 天/分钟**（提速 40 倍） | 日更 wall-clock ≤ 25 min（17:30→17:55）[待验证] | 运行日志 |
| **容量** | 主库 7,366 MB；`index_daily` 1,207 MB 与 `moneyflow` 1,155 MB 为最大两头 | 年增 ≤ 1.5 GB（按当前品类增长）[假设] | 目录体积巡检 |
| **可维护性** | 单真源（config/paths/calendar）+ 36 CLI 子命令 | 新表纳管 ≤ 1 人日（含断言与字典） | 变更记录 |
| **可追溯** | 断点 + 日志 + 留痕；**无快照回滚** | 关键表可按日期回溯 | PoC-2 |
| **隔离性** | `market_data` 只读纪律 + `alt` 硬隔离 | 写通道唯一化（写侧白名单） | 代码守卫 + 抽查 |
| **安全** | 凭据环境变量化（env > `代码/.env` > 空） | 无明文凭据落库/入仓 | `10-安全合规§15.2` |

### 4.2 约束（设计不可逾越）

| 类型 | 约束 | 影响 |
|---|---|---|
| 环境 | Windows 单机、单磁盘（D 盘）、进程式调度 | 无集群/无分布式锁；并发写必须靠**进程纪律**而非锁 |
| 授权 | Tushare 档位（2000 积分/年口径）限频：`daily` 300/分（配 250）、高频组 200/分（配 170）、4 接口 1 次/小时、`index_global` 100 次/天 | 采集必须限速 + 断点续跑；全量重建需分片/错峰 |
| 数据源 | 7 个漏网接口（`share_float`/`index_dailybasic`/`fund_adj`/`opt_daily`/`hk_daily`/`us_daily`/`broker_recommend`）随时可能失效 | 必须有替代源或降级方案（ADR-8） |
| 依赖 | pandas/pyarrow 生态；列存语义（不可行级更新） | 更新以"分区重写 + 去重合并"实现 |
| 人力 | 单人维护 + automation | 机制必须自动化、结论必须机检，禁止靠记忆 |
| 合规 | 数据源授权仅限自用；凭据不可外泄 | 不对外分发、不公开原始数据 |

### 4.3 架构原则（由约束推导，全文引用）

| # | 原则 | 落地 |
|---|---|---|
| P1 | **单一真源** | `config.py` 出规格、`common/paths.py` 出路径、`common/calendar.py` 出日历；禁止 `__file__` 推算与多层 fallback |
| P2 | **布局不可知** | 消费侧只用 `reader` API；禁止从目录/文件名反推数据 |
| P3 | **先落盘后记断点** | 断点表示"数据已在磁盘且可校验"，不是"请求已发出" |
| P4 | **写入通道唯一** | 主干写只经 backfill 引擎 + parquet_store 落盘器；派生层单独通道 |
| P5 | **只读主干** | 消费侧（决策/回测/看板）只读；`alt` 库不写主库 |
| P6 | **显式豁免** | 任何"不参与日更/不建库"的表必须显式登记 + 理由，禁止静默缺失 |
| P7 | **可复核** | 一切结论带 `文件:行号` 或实测命令与日期 |
| P8 | **fail-closed** | 维护链路宁可中断并告警，不可静默降级；决策链路可降级但须显式提示 |
