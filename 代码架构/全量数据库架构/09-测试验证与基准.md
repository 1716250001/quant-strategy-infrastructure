# 09 · 测试、验证与基准（第 14 章）

> 一句话：**数据库的"正确"不靠人看，靠断言说**。本章把"怎么验证库是对的、怎么证明没人把它改坏、性能退化能不能被抓住"三件事写成可执行判据。
> 事实锚点：2026-09-30 实测（`代码/tools/regress_pipeline.py` R1-R16、`tools/db_audit.py` 四类体检、`main.py` 36 子命令）。
> 与 06 §10.7（体检与审计流程）、08 §13（可复现与 digest）、15 §27（质量偏差）配套阅读；验收口径汇总见 16 §32。

## 14.1 测试分层与总体策略

| 层 | 对象 | 现状载体 | 数量级 | 能否阻断发布 |
|---|---|---|---|---|
| L1 单元 | 落盘器/读取器/限频器/日历/路径推导 | `代码/fetch`、`common` 被 `regress` 间接覆盖；无独立 pytest 套件 | 低 | 否（隐性） |
| L2 契约 | `reader` 读取语义、`config` 规格键、布局判定函数 | `regress` R8/R9/R11/R12/R14、`config-check` | 中 | **是** |
| L3 集成 | 日更链路 dry-run、迁移正反向、派生重建 | `regress` R2/R3/R6/R7/R16、`db-migrate` 行数守恒校验 | 中 | **是** |
| L4 数据体检 | 真库（在线数据）断点/重复/缺口/规模/新鲜度 | `db-audit`（四类）、`freshness`、`check-coverage`、`alt-audit` | 高（覆盖 113 目录） | 视类别（core 阻断 / 其余告警） |
| L5 基准 | 日更耗时、补数吞吐、体检耗时、读取延迟 | 无独立基准套件（**缺口**，14.7 补齐） | — | 否（趋势监控） |

**三条纪律（现状已在执行，本文档将其制度化）**：

1. **测试不写生产**：全部断言"只读或 dry-run，不改数据、不消耗额度"（`regress_pipeline.py:10`）。
2. **判据单一真源**：断言不得自行重写一份口径去验另一份口径（R12 通杀条款：`db_audit` 的"应有任务数"必须 `== build_tasks`）。
3. **反向对照**：每条"防过度修复"的断言必须带反例（R15 组 B：普通错误**必须**重试多次；R16 ⑤：非 dry-run 下 spy 必须真被调用）——否则"零请求"可能是假绿。

## 14.2 期望即断言：体检判据体系（L4）

借鉴 Great Expectations"期望即断言"与 Soda"分级告警"（02 §B5）。现状四大体检 + 三条旁路：

| 检查 | 覆盖范围 | 判据 | 分级 |
|---|---|---|---|
| 断点一致性 | 全部有断点的接口 | 断点记录的日期/行数 **==** 磁盘实测（双校验） | core 阻断 |
| 重复检查 | 全部有 `DB_AUDIT_PKEYS` 的表（**114** 键） | 按判重主键分组 `size > 1` 即异常 | 阻断 |
| 缺口检查 | 全部 `BACKFILL_TARGETS`（**101** 项） | 应有任务数 − 已完成任务数；缺口按三类归因 | 分级（下） |
| 规模检查 | 全部 113 目录 | 行数/文件数相对基线的突变 | 告警 |
| 新鲜度 | 日更组 core **7** 表 | 最大日期 ≥ 最近交易日 | 阻断 |
| 覆盖率 | 可转债、ETF/LOF | 标的池覆盖率 | 告警 |
| 规格一致性 | `alt_data` 66 表 + `config_alt` | 表规格与磁盘一致（`alt-audit`） | 告警 |

### 缺口三类归因（`tools/db_audit.py:50-62`）

| 类别 | 判定 | 含义 | 阈值（R12 实测校准） |
|---|---|---|---|
| `日更` | 在 `DAILY_UPDATE_GROUPS` 某组内 | **真缺口**，必须补 | 全体漂移面 **< 500** |
| `豁免` | `freq=day` 但登记在 `DAILY_UPDATE_EXEMPT` | 设计性放弃（附原因） | 独立上界 **< 2,000**（设计性底线实测 424） |
| `周期` | `freq != day`（周/月） | 周期未结束属正常 | 不设预算 |

**为什么拆两条预算**：合并预算会被设计性差额占满（实测正好 500），此后真漂移与已知差额混在一起 → "狼来了" → 真事故反被忽视（`regress_pipeline.py:826-852`）。

**历史事故基线（防复发锚点）**：

| 事故 | 日期 | 表象 | 现已固化的断言 |
|---|---|---|---|
| `shibor` 静默落后 3 天 | 2026-09-21 | `by_range` 全族在断言视野外 | R10 扫描范围纳入 `by_range` |
| `fut_mapping`/`fut_settle` 静默停更 | 2026-09-19 | 只写了属性定义、漏登执行白名单 → `gap-update` 一切正常 | R10「假纳入」判据（mode 必须被引擎支持） |
| `fund_basic` 被 dry-run 写坏 | 2026-09-29 22:35 | 元数据段无 `dry_run` 参数 → 真请求真覆盖写 | R16：`metadata/` 目录指纹前后一致 |
| `fund_basic` 截断（差额 28,004） | 2026-09-29 | `fund_adj`/`fund_share` 各虚增 13,790 | R12 豁免面独立上界 2,000 |
| `shibor_lpr` 误报"还差 13" | 2026-09-20 | `db_audit` 自行按年切分 `single_range` | R12 ④：`single_range` 必须只产生 1 个任务 |

## 14.3 入库前断言（写侧守卫）

写路径上的断言优先于事后体检——**脏数据进了库，体检只能发现它，断言能拦住它**（LakeFS"提交前校验"思想，02 §B3）。

| 守卫 | 位置 | 触发条件 | 行为 |
|---|---|---|---|
| 布局守卫 | `common/parquet_store.py::LayoutGuardError` | 写入器与表布局期望不符（如按年目录写 `{code}.parquet`） | 硬拦抛错，不落盘 |
| 分区守卫 | `upsert_grouped` | 目标表为 `by_year` | 硬拦（防混合布局产生） |
| 去重回合并 | `merge_append` / `upsert_by_year` | 按 `DB_AUDIT_PKEYS` 命中已有行 | 覆盖合并，不追加重复 |
| 迁移守恒校验 | `tools/db_migrate.py:291-299` | `rows_before − rows_after − dedup_removed ≠ 0` | **回滚**，原文件不动 |
| dry-run 零副作用 | 全链路 | `--dry-run` | 零 API 请求 + 零文件写入（R16 断言） |
| 断点后写 | `fetch/backfill.py` | 落盘成功 | 才允许推进断点（**落盘先于记断点**，INV-3） |
| 截断防护 | `by_code` 引擎 | 服务端默认行数上限 < 配置值 | 多轮续拉（上限 `TRUNC_MAX_ROUNDS`）+ 起点回验（R13） |
| 权限不重试 | `fetch/base.py::ts_call_with_retry` | 命中 `_is_permission_error` | 1 次调用即返回（实测重试 5 次白等 18.5 秒） |

**to-be（PoC-1 兑现项）**：列级断言（dtype/单位/可空/枚举，05 §20.4）在**落盘前**执行——列名集合、dtype 与规格不符即拒收；单位与枚举违例记报告。

## 14.4 回归断言集：16 组 / 28 检查项（L2-L3 核心）

`python main.py regress`（`tools/regress_pipeline.py`），退出码即门禁（非零 = 有失败）。

| 组 | 名称 | 核心判据（防什么） |
|---|---|---|
| R1 | CLI 注册完整 | 36 子命令 `--help` 可执行；收编后活入口（`leverage`/`etf-flow`/`gap-update`）在册；旧平铺名仍为隐藏别名（**契约白名单依赖其存在**） |
| R2 | 每日增量缺口计算 | core 组完整存在 + 成员均能取到属性定义；**不硬编码接口数量**（断言结构性质，防脆弱测试） |
| R3 | 限频器按接口生效 | 按接口独立配额，预约式不互相挤占 |
| R4 | `fund_nav`/`redtide_supply` 可导入 | 模块面未破 |
| R5 | 归档件收编 | 盘后三步归档后，活入口仍可导入 |
| R6 | 限频行为核对 | 实际间隔 ≥ 配置间隔（防"配置了但没生效"） |
| R7 | 废弃引擎守卫 | `gap_update`/`intraday_update` 调用必须抛 `DeprecatedEngineError`（**不得静默跑错**） |
| R8 | 全库布局一致性 | 除刻意的 `stock_company` 外**不应再有 `by_code` 表**；不应有混合布局 |
| R9 | 布局期望与写入器守卫 | `table_storage_layout`（单一真源）与磁盘不分歧；`upsert_grouped` 硬拦按年目录 |
| R10 | 每日更新清单完整性 | `BACKFILL_TARGETS` ↔ `DAILY_UPDATE_GROUPS` 双向；③freq≠day 机制豁免；**「假纳入」**（组内 mode 不被引擎支持）必须报错 |
| R11 | 配置完整性 | 条目数下限（防误删）、关键常量、判重主键、组结构、键名有效性、正反向覆盖 |
| R12 | 缺口分析口径一致性 | `_period_key` 四端点规范化、周期折算、`db_audit.expect == build_tasks`、`single_range` 只产 1 任务、漂移面/豁免面双上界 |
| R13 | `by_code` 截断防护 | 库内起点不得晚于源端已知起点；判据不得写成 `len(df)==max_rows`（会漏判续拉） |
| R14 | 联查层契约（alt↔主库） | ①低匹配率必须告警（默认 `how='left'` 匹配率仅 3.3% 却"有输出不报错"）②容差方向自动识别（传参顺序反了不报错）③列名错必须抛 `KeyError` ④日期列口径 |
| R15 | 权限漏网监控 | 权限错误识别（不误伤限频/网络）、1 次调用、记录器、`LEAKY_PERMISSIONS` 清单与表定义交叉验证（`claimed/kind/use/alt/monitor` 字段齐全） |
| R16 | dry-run 零副作用 | `metadata/` 指纹（相对路径+size+mtime_ns 逐文件）前后一致 + 计划已打印 + **反向对照**（非 dry-run 必须真调） |

**何时跑（纪律，沿用现状）**：改动数据层 / 存储布局 / 每日更新链路**之后**；另建议每周一次定时跑（16 §32.4 门禁表）。

**扩展原则（to-be）**：新增任何"两个本该联动的结构"（如新增组、新增模式、新增别名），必须同步新增一组断言——**R10/R12 的四次复发同源**（`mode↔layout`、`TARGETS↔GROUPS`、`CLI 注册表↔回归白名单`、`backfill_spec↔db_audit 任务计算`），教训是"两个结构各管一摊"必然漂移。

## 14.5 契约测试与 schema 演进验证

| 契约 | 验证方式 | 现状 |
|---|---|---|
| 读侧语义（`read_code`/`read_range`/`list_codes`/`latest_date`） | 布局无关性测试：同一表在 `by_year`/`single`/`by_code` 三种布局下结果一致 | 靠 R8/R9 间接守护；**无独立契约测试**（缺口） |
| 列名与 dtype | `db-schema` 导出列清单 + `schema_hash`（08 §13.4）比对 | 有导出、**无断言** |
| 日期列 | `TABLE_DATE_COL`（**79** 项）驱动；表内日期列必须存在 | R11 覆盖键名有效性 |
| 判重主键 | `DB_AUDIT_PKEYS`（**114** 键）键名必须真实存在于该表列 | R11（"键存在但列不存在"盲区已封） |
| 取数模式 ↔ 布局 | `table_storage_layout` 单一真源 | R9 |

**列级变更登记流程（to-be，PoC-1）**：

```
改列（增/删/改类型/改单位）
  → ① 更新 config.py 列级规格（唯一真源）
  → ② 跑 db-schema --json，diff 出生新旧 schema_hash
  → ③ schema_hash 变化即触发：文档（05 §20.2）重生成 + 消费侧通知 + 快照 manifest 登记
  → ④ 验收：regress 全绿 + 受影响黄金集（14.9）通过
```

**判定规则**：`schema_hash` 变化 = **不兼容事件**（除非仅为新增可空列且消费侧未引用）；无声变化（未登记却 hash 变了）= 缺陷，按 15 §27 质量事故处理。

## 14.6 数据指纹与对账测试

| 手段 | 用途 | 判据 | 现状 |
|---|---|---|---|
| 重跑一致（幂等） | 同一目标日跑两次 `gap-update`，库内容不变 | digest 逐位一致（08 §13.2/§13.4） | 机制具备，**无自动断言**（PoC-4） |
| 快照比对 | 变更前后 `manifest.json` 行数/摘要 | 差异集 == 预期变更表集 | 无（PoC-2） |
| 双源对账 | `alt_data` vs 主库重叠表 | 差异可解释（复权/汇率/日历），不可解释差异须归因 | R14 覆盖联查契约；对账未自动化 |
| 报告对账 | 看板/日报中的数字 vs 直接查库 | 逐项可复算 | 现由人工抽检 |
| 反向依赖检查 | 派生表只读主干 | 主干目录 mtime 不因派生任务变化 | INV-7，无自动断言 |

**对账测试的定位**：不是"两库必须相等"（口径本就不同），而是"**差异必须能被口径解释**"——无法解释的差异即缺陷，须登记（15 §27.2）。

## 14.7 性能与容量基准（L5，to-be 主体）

**现状**：无独立基准套件；性能事实散落在运行日志与人工实测中。**这是本章最大缺口**，建议以"基准清单 + 基线数字 + 退化阈值"三件套补齐。

### 基准清单（建议起点）

| # | 基准 | 方法 | 关注量 | 退化阈值（建议） |
|---|---|---|---|---|
| B1 | 日更端到端 | 定版后同一交易日重放（或 dry-run + 抽样真跑） | 总耗时、每接口耗时、失败数 | 总耗时 > 基线 ×1.5 |
| B2 | 单接口吞吐 | 单表 `backfill --only` 全历史 | 行/秒、分页轮数 | 吞吐下降 > 30% |
| B3 | 补数（缺口批量） | 已知缺口批次重放 | 任务/分钟、额度消耗 | 同 B2 |
| B4 | 体检耗时 | `db-audit` 全量 | 秒（现为人工观感） | > 基线 ×1.5 |
| B5 | 读取延迟 | 冷/热两种状态下的 `read_range`（1 年切片） | ms | > 基线 ×2 |
| B6 | 列裁剪收益 | `daily_basic` 全列 vs 仅需列 | 体积比、耗时比 | 收益回落 > 50% |
| B7 | 迁移耗时 | `by_code → by_year` 单表 | 秒/万行 | 同 B2 |

### 已实测的容量事实（可作基线锚点，2026-09-30）

| 事实 | 数值 |
|---|---|
| 全库规模 | 113 目录 / 10,852 文件 / **7,366 MB** / 291,396,574 行 |
| `by_year` 大表单年体积 | 12~35 MB（`index_daily` 单年 35 MB 最大） |
| 单文件均值 | 约 0.68 MB |
| 列宽效应 | `daily_basic` 与 `daily` 行数同量级但体积为其 **2 倍** → 列裁剪收益显著（B6 依据） |
| Top5 体积占比 | `index_daily`+`moneyflow`+`daily_basic`+`wind_index`+`daily` ≈ 全库 **58%** |
| 迁移收益（历史实证） | `moneyflow` 迁移至 `by_year` 后 **1 天/分 → 41 天/分**（约 40×） |

**采集方式（to-be）**：每次日更/补数写一行基准记录（`metadata/bench_log.jsonl`），含 `date / task / rows / seconds / api_calls`；退化判定由趋势线给出，**不设硬门禁**（避免机器抖动误报），超阈值才告警。

## 14.8 故障注入与恢复演练

| 演练 | 注入方式 | 期望行为 | 频率 |
|---|---|---|---|
| 断点虚记 | 手工改断点为未来日期 | `ckpt --verify` 抓出不一致并报错 | 变更后 |
| 断点漏记 | 落盘后不推进断点 | 重跑幂等（去重合并，行数不变） | 变更后 |
| 半途中断 | 日更中途杀进程 | 已完成表保留、断点三态（done/partial/failed）不谎报；重跑只补缺失 | 季度 |
| 磁盘满/只读 | 目录置只读 | 落盘失败 → 断点不推进 → 显式报错（不静默） | 季度 |
| 权限被收紧 | 用无权限接口跑 | 1 次调用即停 + 命中 `LEAKY_PERMISSIONS` 时给出替代路径告警 | 变更后 |
| 服务端截断 | 强制小 `max_rows` | 多轮续拉 + 起点回验通过 | 变更后 |
| 回滚演练 | 从 `_snapshots/` 恢复单表 | 回滚 ≤ 5 分钟；`db-audit` 与快照 manifest 一致 | PoC-2 验收 |

**判据共性**：**失败必须可见**（15 §28.2 分级告警）——"静默失败"是唯一不可接受的失败形态。

## 14.10 验收判据与门禁

### 库级 SLO（与 01 §质量属性、14 §22.4 共用一套）

| SLO | 指标 | 目标 |
|---|---|---|
| S1 日更成功率 | `core` 7 表当日推进到最近交易日 | ≥ 99% 交易日 |
| S2 数据新鲜度 | core 表最大日期 = 最近交易日 | 滞后 ≤ 1 交易日 |
| S3 体检可信度 | 断点一致率（断点 == 磁盘） | 100% |
| S4 重复率 | 按主键重复行数 | 0 |
| S5 真缺口 | `日更`类未补任务数 | < 500 且无 core 表在列 |
| S6 可复算 | 快照 manifest 比对一致率 | 100%（PoC-2 后生效） |
