## 章 16 · 演进路线与 MVP 建议

### 16.1 MVP 边界（承接 01 §2.2，不重复论证）

| 分类 | 内容 |
|---|---|
| **保持不动（已服役）** | 单机 Parquet 数据湖 + 目录即分区；`config.py` 单一真源；`fetch/*` 八种取数模式 + 落盘器；`reader` 读侧契约；36 CLI 子命令；断点三态；`regress`/`db-audit` 体检链；WorkBuddy 日更 17:30 |
| **MVP 增量（本节 16.2）** | K1 表规格机读真源 · K2 快照与回滚 · K3 库级 SLO 看板 |
| **明确不做** | 数据库引擎/分布式/对象存储/流式采集/分钟级与 Level2 入库/统一两套读取层（N1-N7，ADR-1/4、12 号） |
| **暂缓（有触发条件）** | DuckDB 读侧加速、写锁、环境固化、替代源补全、分发登记表（16.3 阶段 2/3） |

### 16.2 MVP 增量三件事（K1 / K2 / K3）

| # | 目标 | 产出物 | 验收锚点 | 预估 | 依赖 |
|---|---|---|---|---|---|
| **K1** | 表规格机读真源：文档与校验都由 `config.py` 生成 | `db-schema --json` 增补列级字段（dtype/单位/可空/枚举）+ 05 §20.2 字典与 README 快照表由脚本渲染 | `schema_hash` 可 diff；字典与库零偏差；落盘前列级断言生效 | 中 | PoC-1 |
| **K2** | 关键表快照与回滚：回答"那天库是什么样" | `_snapshots/YYYY-MM-DD/manifest.json`（行数+schema_hash+digest）+ 4 步回滚流程 | 单表回滚 ≤ 5 min；回滚后 `db-audit` 与 manifest 完全一致；不触碰其它表 | 中 | PoC-2 |
| **K3** | 库级 SLO 看板：把体检从"人工跑"变成"每日打分 + 异常推送" | 6 项 SLO（09 §14.10）每日打分 + 一页看板/日报段落 | 每日自动产出结论；core 异常当日推送 | 小 | 现有 `db-audit`/`freshness` 输出 |

**为什么是这三件**：现状唯一的高危缺口是**"无法回答当时是多少"**（K2）与**"口径靠人记"**（K1）；K3 是让前两者被持续观察的最低成本手段（13 号 §19.3 Streamlit 看板即其载体）。

### 16.3 路线图（四阶段，不设硬日期）

```
阶段 0（现状，持续）   在线服役：日更 17:30 + 每周体检 + 变更后 regress
        │
阶段 1（MVP 增量）     K1 → K2 → K3   （先验收 PoC-1/2，再落地）
        │
阶段 2（治理硬化）     写锁(PoC-5) · 环境固化(PoC-6) · alt 对账 · 替代源补全(ADR-8) · 基准套件(09 §14.7)
        │
阶段 3（可选能力）     DuckDB 读侧加速 · 静态 HTML 历史对比 · 新布局(by_month) · 分钟级通道探索
```

**阶段升级触发的硬条件（禁止"感觉需要就上"）**：

| 升级 | 触发条件 |
|---|---|
| 阶段 2 写锁 | 出现并发写/第二个写进程（现状单进程假设 [风险] R-并发写） |
| 阶段 2 基准套件 | 出现"说不清为什么变慢"的情况 |
| 阶段 3 DuckDB | 体检/全市场回放成为明显瓶颈（单次 > 10 min [假设]） |
| 阶段 3 新布局 | 单年文件 > 2 GB 或某表年增 > 500 MB [假设] |
| 引入引擎 | 表数 > 200 或参与方 > 3 人（07 §12.10 重估触发） |

### 16.4 里程碑与验收锚点

| 里程碑 | 达标标志 |
|---|---|
| M0（现状已达成） | 日更连续稳定；`regress` 16 组全绿；`db-audit` 无阻断异常 |
| M1（K1+K2 落地） | 字典由真源生成；单表回滚演练通过；快照 manifest 可比对 |
| M2（K3 落地） | SLO 日报自动产出；连续 20 个交易日 core 达标率 ≥ 99% |
| M3（阶段 2 完成） | 写锁 + 基准 + 对账在册；停更/漏网清单季度复核成例行 |

## 章 17 · 风险登记与开放问题

### 17.1 风险登记表

**等级**：P=概率（高/中/低）· I=影响（高/中/低）· 状态（开放/缓解中/已建档）。

| ID | 风险 | P | I | 缓解措施 | 触发信号 | 状态 |
|---|---|---|---|---|---|---|
| R-1 | **磁盘单点**：单盘无冗余，物理损坏即全库丢失 | 低 | **高** | 冷备（周期性 copy 到独立介质）+ 重拉能力（PoC-2 覆盖回滚侧） | 任何 IO 异常/坏道 | 缓解中 |
| R-2 | **授权收紧**：7 项漏网接口被平台关闭 | 中 | 高 | `LEAKY_PERMISSIONS` 监控 + 替代路径 + 升档评估（10 §15.3） | 连续 3 交易日无权限 | 缓解中 |
| R-3 | **停更表被误当现状**：`gz_index`(止 2019)、Wind 指数(止 2026-09-21) | 中 | 中 | 停更显式清单（GS-6）+ 新鲜度阈值分级 | 消费侧引用停更线 | 缓解中 |
| R-4 | **并发写**：写锁缺失，两个进程同写一表可能交错 | 低 | 高 | 单进程纪律；PoC-5 写锁 | 出现第二个写进程 | 开放 |
| R-5 | **无快照/回滚**：覆盖写不可回溯，误覆盖只能重拉 | **高** | 高 | K2 快照层 + manifest + 4 步回滚 | 任何误覆盖事故 | 缓解中 |
| R-6 | **静默失败**：数据逐日变旧而不报错（已 4 次复发：清单漏登/断言视野外/元数据段无 dry-run/假纳入） | 中 | 高 | 断言 + 分级告警 + "静默失败即违规"（15.5） | 体检发现落后 N 天 | 缓解中 |
| R-7 | **凭据单点**：三把钥匙单人保管，失效即全停 | 中 | 高 | 离线备份 + 恢复文档 + 失效告警降级链 | 令牌过期/失效 | 开放 |
| R-8 | **派生输入版本未登记**：派生物无法复算（输入变了但没记） | 中 | 中 | 派生 manifest（输入表版本清单，14 §26.4） | 派生结论不可复现 | 开放 |
| R-9 | **文档数字与真源漂移**：README/字典手抄实测值，会过期 | **高** | 中 | K1 由真源渲染 + 每次修订登记（README §七） | 抽查发现数字不符 | 缓解中 |
| R-10 | **隔离靠约定**：只读纪律依赖人的自觉，文件系统仍可写 | 中 | 高 | 写通道收敛 + 只读挂载建议 + `assert_writable` 硬保护（alt 侧已有） | 出现旁路写入 | 缓解中 |
| R-11 | **源方修正窗口短**：源数据回溯修正后，库内旧值无告警 | 中 | 中 | 复核窗口 + 修正检测（PoC-3） | 两源对账出现不可解释差异 | 开放 |
| R-12 | **规模增长失控**：Top5 表占 58% 体积，无归档策略 | 低 | 中 | 体量热点监控（05 §20.3）+ 冷备分级 | 年增 > 500 MB/表 | 开放 |
| R-13 | **单源依赖**：`us_daily` 限频 1 次/小时、历史回补不可行（≈377 天） | 中 | 中 | 历史用 akshare 新浪源补；日更足够 | 需重建美股历史 | 缓解中 |

## 章 21 · 下一步 PoC 与验证清单

**PoC 纪律**：每个 PoC 必须**只读或可回滚**（不破坏在线库）、有**明确验收判据**、有**失败处置**（失败就记结论并调整方案，不做"跑通即算"）。

### 21.1 PoC 总览

| # | 主题 | 目标 | 验收判据（硬） | 顺序 |
|---|---|---|---|---|
| PoC-1 | 列级契约机读化 | 证明"表规格 → 文档 + 落盘前断言"可自动化 | ① `db-schema --json` 含四类列级字段 ② 字典由脚本生成、与库零偏差 ③ 注入一列类型错误能被拒收 | 第 1 |
| PoC-2 | 快照与回滚 | 证明"任一时点可回溯"低成本可行 | ① 单表回滚 ≤ 5 min ② 回滚后 `db-audit` 与 manifest 完全一致 ③ 其它表 mtime 不变 ④ 最小验收：**按标的可追溯**（如 `000001.SZ` 全历史） | 第 2 |
| PoC-3 | 源方修正检测 | 证明"旧值被改"可被发现 | ① 对选定表连续 N 日比对 digest ② 构造一次真实修正（或模拟）能被检出 ③ 误报率可接受 | 第 3 |
| PoC-4 | 幂等与运行台账 | 证明"重跑零变化"可机检 | ① 同一日两次 `gap-update` 后 digest 逐位一致 ② `RunLedger` 能回答"该行来自哪次运行" ③ 断点与台账一致 | 第 3（可与 PoC-2 并行） |
| PoC-5 | 写锁 | 证明并发写可被阻断 | ① 第二个写进程被拒绝并给出明确提示 ② 崩溃后锁可自动失效（无"死锁无人能写"） | 第 4 |
| PoC-6 | 环境固化 | 证明换机可复现 | ① `requirements.txt`/`pyproject.toml` 冻结版本 ② 新机按文档可拉起并跑通 `regress` | 第 4 |

### 21.2 PoC 与 MVP/路线图的映射

| PoC | 兑现的 MVP 项 | 兑现的风险缓解 |
|---|---|---|
| PoC-1 | K1 | R-9（文档漂移） |
| PoC-2 | K2 | R-5（无快照）、R-1（恢复能力） |
| PoC-3 | — | R-11（修正窗口短） |
| PoC-4 | K2 辅助 | R-6（静默失败）、R-8（派生输入版本） |
| PoC-5 | 阶段 2 | R-4（并发写） |
| PoC-6 | 阶段 2 | R-7（凭据/环境单点） |

### 21.3 依赖与顺序图

```
PoC-1（列级契约）──┐
                   ├─▶ K1 落地 ──▶ 文档由真源生成（消除 R-9）
PoC-2（快照回滚）──┴─▶ K2 落地 ──▶ 快照 + 回滚（消除 R-5）
        │
        └─▶ PoC-4（幂等/台账，可并行）
                     │
PoC-3（修正检测）◀───┘（需要 digest 能力，依赖 PoC-4 的指纹实现）
                     │
PoC-5（写锁） · PoC-6（环境固化）──▶ 阶段 2
```

### 21.4 每个 PoC 的失败处置（预设）

| PoC | 失败形态 | 处置 |
|---|---|---|
| PoC-1 | 列级字段无法自动导出/维护成本过高 | 降级为"仅关键 20 表列级契约"；其余表保留现状导出 |
| PoC-2 | 快照体积/耗时不可接受 | 降级为"仅元数据 + 小表快照"；大表用 digest 指纹替代（08 §13.4） |
| PoC-3 | 误报率高（正常修正频繁） | 扩大复核窗口；改为"季度全量比对"而非逐日 |
| PoC-4 | digest 计算成本高 | 采样 digest + 行数/schema_hash 组合判据 |
| PoC-5 | 锁机制引入运维负担 | 保持"单进程纪律 + 启动时检测写进程"轻量方案 |
| PoC-6 | 依赖无法完全冻结（三方库漂移） | 记录实测版本指纹（env 指纹），不做强冻结 |
