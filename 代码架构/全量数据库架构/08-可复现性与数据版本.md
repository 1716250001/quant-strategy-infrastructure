# 08 · 可复现性与数据版本（章 13）

> 命题：**"同一天跑同一个策略，必须得到同一个结果"**。这在数据侧等价于三件事：写入幂等、库状态可标识、历史状态可重建。
> 现状：前两件**已具备机制**；第三件**缺失**（无快照/无回滚），是本文档识别的第一优先缺口。

---

## 13.1 可复现性的三层

| 层 | 含义 | 现状 |
|---|---|---|
| R1 写入幂等 | 同一批数据重复执行，库内容不变 | **具备**：落盘器按 `DB_AUDIT_PKEYS` 去重合并；复核窗口重拉；无参快照表排除 |
| R2 状态可标识 | 任一时刻的库状态可用**版本号/摘要**标识并被引用 | **部分具备**：行数与文件数可查，但无"版本号"，无逐表摘要清单 |
| R3 历史可重建 | 任一时点的库状态可重建（回滚或重放） | **缺失**：覆盖写不可逆；误覆盖只能靠重拉接口 [风险 R-1] |

## 13.2 幂等的实现细节（现状机制）

| 机制 | 落点 | 说明 |
|---|---|---|
| 去重合并 | 落盘器 `merge_append` / `upsert_by_year` / `upsert_grouped`（`dedup_subset` 默认取 `DB_AUDIT_PKEYS` 口径） | 同主键重复写 → 覆盖而非追加 |
| 复核窗口 | 日更 `resolve_gaps` 的 `lookback`（重拉最近若干交易日） | 源方事后修正可被吸收（**重复执行安全**的前提） |
| 无参快照表排除 | `once` 类表不进日更 | 避免"无参数调用"造成脏写 |
| 批量落盘器 | `YearBatchWriter` / `ByCodeBatchWriter` | 同批多标的一次写入，避免逐行读-改-写 |
| 断点态保护 | `partial` 保留游标续跑；`failed` 不推进 | 失败不会伪装成完成 |

**幂等验收命令**（可直接执行）：

```
main.py gap-update --table daily --start 20260925 --end 20260929   # 重复跑一次
main.py db-audit                                                    # 重复体检应为 0
```

## 13.3 快照与回滚（to-be，PoC-2）

### 目标形态（不侵入主干路径）

```
D:\全量数据\market_data\
├── _snapshots/                      # 新增：快照根（不参与任何读取路径）
│   ├── 2026-09-30/
│   │   ├── manifest.json            # 表 → {文件, 行数, MB, digest, schema_hash}
│   │   └── daily/2026.parquet       # 硬链接或副本（优先硬链接，零额外空间）
│   └── 2026-W40/                    # 周快照（保留更久）
└── （主干目录保持不变）
```

### 保留策略（建议起点）

| 粒度 | 保留 | 体积估计 |
|---|---|---|
| 日快照 | 最近 **5 个交易日**（仅核心 7 表 + 派生状态） | 日增约 100~150 MB [假设]（硬链接可降至接近 0） |
| 周快照 | 最近 **8 周**（全库清单 + 大表文件） | 按需 |
| 月快照 | **12 个月**（仅 manifest + 关键表） | 小 |

### 回滚流程（4 步）

| 步 | 动作 | 守卫 |
|---|---|---|
| 1 | 触发条件确认（数据错误/误覆盖/迁移失败） | 记录事故与影响表 |
| 2 | 选择目标快照 | `manifest.json` 校验 digest 匹配 |
| 3 | 恢复（按表 + 按分区，原子替换） | 恢复前先对当前状态做一次"抢救快照" |
| 4 | 校验与销项 | `ckpt --verify` + `db-audit` + 相关断言全绿 |

**验收判据（PoC-2）**：① 单表回滚 ≤ 5 分钟；② 回滚后 `db-audit` 与回滚前快照的 `manifest` 行数/摘要**完全一致**；③ 回滚过程不修改主干其它表。

## 13.4 内容摘要指纹（digest）

| 指纹 | 计算方式（建议） | 用途 |
|---|---|---|
| `rows` | 行数（廉价、强判据） | 突变检测、快照比对 |
| `schema_hash` | 列名 + dtype 排序后的哈希 | 捕捉静默改列 |
| `content_digest` | 按主键排序后取 `(pkey, 关键数值列)` 的哈希（或采样哈希） | 精确比对"内容是否同一份" |
| `file_digest` | 文件级哈希（仅小表/元数据表） | 静态表完整性 |

**为什么不用全量文件哈希**：`by_year` 大表 20~35 MB，全库哈希成本高；**行数 + schema_hash + 采样 digest** 足以支撑"是否被篡改/漂移"的判断 [待验证：采样比例与漏检率]。

## 13.5 数据版本与"时间旅行"

**轻量版本号（建议）**：`MD-YYYYMMDD.N`（N = 当日第 N 次成功日更/变更），记录在：

```
D:\全量数据\market_data\metadata\db_version.json     # 或库根 .db_version.json
{
  "version": "MD-20260930.1",
  "generated_at": "2026-09-30T17:52:13+08:00",
  "tables_changed": ["daily", "daily_basic", "..."],
  "manifest": "_snapshots/2026-09-30/manifest.json",
  "checkpoint_rev": "..."
}
```

**消费侧引用方式**：回测产物与研究报告在元数据中记录 `db_version`（及必要时的 `manifest` 路径），从而**可回答"这份结果基于哪个库版本"**（对照回测侧的可复现纪律）。

## 13.6 重放与重建（RTO/RPO）

| 场景 | 现状 | 目标（建议） | 判据 |
|---|---|---|---|
| 单表误覆盖 | 重拉接口（可能受权限/停更限制） | 快照回滚 | ≤ 5 min（PoC-2） |
| 全盘损坏 | 冷备 + 全量重建（耗时未知） | 冷备恢复 + 增量重拉 | RTO ≤ 24 h；RPO ≤ 1 交易日 [待验证] |
| 断点丢失 | 由磁盘重算缺口（可行） | 保持 | `gap-update` 可无断点冷启动 |
| 源方数据修正 | 复核窗口吸收（仅最近几日） | 快照 + 修正检测 | 修正窗口 > 3 日时需人工介入 [开放问题] |
| 停更表 | 无替代（`gz_index` 止 2019、Wind 指数止 09-21） | 替代源或显式冻结 | 停更清单与新鲜度阈值（15 §27.4） |

## 13.7 与消费侧可复现的接口

| 要求 | 说明 |
|---|---|
| 回测产物须记 `db_version` | 否则"同策略不同结果"无法定位到底是库变了还是代码变了 |
| 派生表须记输入版本 | 派生表 = f(主干版本, 派生逻辑版本)，两者都要记 |
| 消费侧禁止"取当前最新" | 若策略回测依赖 `latest_with_data()`（决策侧 API），**回测场景必须固定日期**，否则不可复现 [风险 R-7] |
| 影子数据 | 消费侧若在库外缓存数据（如 ROE 缓存），须记缓存版本与失效条件（14 §23.5） |

## 13.8 现状差距与改进映射

| 差距 | 风险等级 | 改进 | 落点 |
|---|---|---|---|
| 无快照/回滚 | **高** | 快照层 + manifest + 回滚流程 | PoC-2（11 §21） |
| 无库版本号 | 中 | `db_version.json` + 消费侧登记 | 13.5 |
| 无逐表摘要 | 中 | manifest 中加 `rows/schema_hash/digest` | PoC-1/2 |
| 断点与运行无台账 | 中 | `RunLedger`（04 §8.6） | PoC-4 |
| 源方修正窗口短 | 中 | 扩大复核窗口 / 修正检测 | 11 §21 PoC-3 |
| 派生输入版本未登记 | 中 | 派生 manifest（输入表版本清单） | 14 §26.4 |
