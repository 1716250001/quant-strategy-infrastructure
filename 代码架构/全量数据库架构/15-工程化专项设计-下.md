## 章 27 · 质量与偏差治理

### 27.1 偏差来源五分类

| 类 | 来源 | 典型 | 现状处置 |
|---|---|---|---|
| S 源偏差 | 源方口径变更、回溯修正、错值 | 源方事后修正历史值 | 复核窗口 + 修正检测（PoC-3） |
| F 取数偏差 | 截断、分页漏页、参数被忽略、限频中止 | `us_basic` 5 页、`fut_weekly_detail` 参数忽略 | R13 + `SUSPECT_CAPS` + `truncated` 告警 |
| W 写入偏差 | 覆盖写、混合布局、重复固化、半写 | `fund_basic` 被 dry-run 覆盖写；首次建库固化重复 | R16 指纹 + 布局守卫 + 去重合并 |
| N 口径偏差 | 单位、复权、频率锚点、日期格式 | `amount` 曾"千元/元"不一致；周锚点误用 `last_trade` | K1 列级契约（`unit`）+ 23.3 |
| T 时间偏差 | 断点超前/落后、时区、交易日历错配 | 断点虚记；`by_range` 静默落后 3 天 | 断点三态 + 双校验 + R10 |

### 27.2 判定与归因：**不可解释的差异就是缺陷**

**核心判据**（INV-10 的数据面体现）：任何一次查询/体检/对账中出现的差异，必须能被 ① 口径差异 ② 已知豁免 ③ 已登记变更 三者之一解释；**解释不了 = 缺陷**，不得以"可能是源的问题"结案。

| 差异形态 | 可解释的归因（举例） | 不可解释 → 动作 |
|---|---|---|
| 行数变化 | 新增交易日 / 源方补历史 / 去重修复 | 登记变更 + 进入偏差台账 |
| 数值变化 | 源方回溯修正（PoC-3 检出）/ 单位修正事件 | 追查变更来源；无 `db_version` 记录即违规 |
| 覆盖率下降 | 停牌 / 新标的未入池 / 源方下架 | `check-coverage` 分类判定 |
| 缺口增加 | 授权收紧（漏网被拒）/ 日历错配 | 按 09 §14.2 三类归因；`日更`类直接告警 |
| 匹配率下降（联查） | 键格式变化 / 日期口径错 | R14 ① 告警；不得静默 |

### 27.3 派生幂等与重建（INV-7）

| 要求 | 判据 | 现状 |
|---|---|---|
| 同输入必同输出 | 同一输入集重跑，输出 digest 一致 | 派生脚本无 digest 断言（gap） |
| 只读主干 | 主干目录 mtime 不因派生任务变化 | 无自动断言（gap） |
| 可全量重建 | 删除派生输出后一条命令重建，结果等价 | 可重建，成本未测 |
| 输入版本可追溯 | 派生 manifest（输入表 + `date_max` + `db_version`） | **未登记**（R-8） |
| 不得反向写主干 | 派生输出仅在白名单目录 | 是（`market_state`/`custom_index`/`signals`） |

**治理动作**：删除派生输出不是灾难（可重建），**但输入版本未记 = 重建不可复现**——这是本节首要补强项（PoC-4）。

### 27.4 新鲜度、停更与空值语义

**新鲜度阈值（建议分级，K3 采用）**：

| 级别 | 判定 | 告警 |
|---|---|---|
| OK | 滞后 0 交易日 | 静默 |
| 提示 | 滞后 1 交易日（core 表当日未更） | 日报提示 |
| 告警 | 滞后 ≥ 2 交易日 | 立即告警 |
| 静音（非故障） | 表在**停更清单**或**周期表未到期**或**豁免清单** | 不告警（防狼来了） |

**停更清单（现状）**：`gz_index`（止 **2019-03-04**）、`wind_index`（止 2026-09-21，3,182 文件）；另有**源端停更但接口可调**的两类——`stk_account`（止 2019-02-22）与金十系海外宏观 14 张（源端停更 2025-08~10，spec 已标 `known_stale`，当期用东财系替代）。规则：**停更 = 事实状态 + 显式记录 + 复核日期**；停更表仍在库（历史不可再生），但消费侧不得当作"最新"。

**空值语义（必须在文档与断言中显式）**：

| 空值含义 | 例子 | 消费侧动作 |
|---|---|---|
| 行业不适用 | 财务表非适用行业字段 | 过滤 |
| 亏损无意义 | `pe` 为负/为空 | 过滤（不得填 0） |
| 当日无交易 | 停牌、指数品种无数据 | 属正常（`check-coverage` 判定） |
| 源方缺失 | 未披露/未收录 | 标为缺口或豁免，不静默填 |

**判据**：**空 ≠ 0 ≠ 缺失**；任何"把空当 0"的处理必须在消费侧显式声明（否则属于静默偏差）。

### 27.5 质量事故分级与处置

| 级别 | 定义 | 例子 | 处置时限（建议） |
|---|---|---|---|
| **P0** | 主干数据被破坏或不可用 | 覆盖写事故；整表丢失 | 立即止损（回滚/停写）→ 修复 → 根因 → 新增断言 |
| **P1** | 关键表长时间静默落后/错误 | `shibor` 落后 3 天；`fund_basic` 截断 28,004 | 当日定位 → 补数 → 断言固化 |
| **P2** | 非核心表偏差、覆盖率下降 | 个别 `alt` 表口径漂移 | 周内处理 |
| **P3** | 文档/报告数字不符 | 字典与库不一致（R-9） | 下次修订（K1 后为不可能） |

**处置闭环模板**：`现象 → 范围（表/日期/影响面）→ 根因 → 已采取的止损 → 新增的断言 → 偏差台账登记`。

### 27.6 偏差台账（建议载体）

`metadata/quality_log.jsonl`，每行一条：`日期 / 表 / 类别（S/F/W/N/T）/ 现象 / 归因 / 解释或缺陷 / 处置 / 关联断言`。**作用**：把"事故"变成"可查询的历史"，让复发可被识别（本库 4 次复发同源，都是台账缺失导致的记忆问题）。

## 章 28 · 可观测性与告警

### 28.1 观测面（五面）

| 面 | 载体 | 回答的问题 |
|---|---|---|
| 运行面 | 日更/补数日志 | 今天跑了什么、成功多少、耗时 |
| 状态面 | 断点 JSON（三态）+ `ckpt --show` | 数据到哪儿了、可信吗 |
| 体检面 | `db-audit` / `freshness` / `check-coverage` / `alt-audit` | 缺什么、重不重、新不新 |
| 元数据面 | `db-schema` / `db_version.json` / 快照 manifest | 库长什么样、变过什么 |
| 趋势面 | `bench_log.jsonl`（09 §14.7，to-be） | 变快了还是变慢了 |

### 28.2 分级告警（本章重点）

| 级别 | 触发 | 通道 | 期望响应 |
|---|---|---|---|
| **P0 阻断** | 覆盖写/写失败/断点虚记/`core` 表当日全败 | PushPlus **即时** + 控制台 | 立即人工介入 |
| **P1 告警** | core 表滞后 ≥ 2 交易日；漏网接口被拒（`monitor=True`）；重复行 > 0；真缺口含 core 表 | PushPlus 日更汇总 | 当日或次日处理 |
| **P2 提示** | 非核心表缺口、覆盖率下降、体积突变、基准退化 | 日报段落 | 周内处理 |
| **静音** | 停更清单 / 周期表未到期 / 显式豁免 / 已知设计性差额 | 无 | 按复核日期复查 |

**三条铁律**：

1. **静默失败即违规**：任何失败必须落到日志或告警；"没消息"只能是"真没事"（09 §14.8）。
2. **防狼来了**：已知差额（豁免/停更）必须静音，否则真报警被淹没——历史上"合并预算被设计性差额占满"即此类（09 §14.2）。
3. **告警不可自证清白**：告警通道自身失效（`PUSHPLUS_TOKEN` 过期）必须有降级（控制台输出 + 次日体检发现）（10 §15.2）。

### 28.3 告警内容契约（缺一不可）

```
[级别] 表名 · 日期范围 · 类别（权限/缺口/重复/截断/失败）
现象：一句话（如"shibor 落后 3 个交易日"）
影响：哪些消费侧会受影响
建议动作：一条可执行命令（如 main.py gap-update --only shibor）
参考：断言 ID 或偏差台账编号
```

### 28.4 告警治理

| 问题 | 治理 |
|---|---|
| 重复告警 | 同一现象 24h 内合并；持续未处理升级级别 |
| 告警疲劳 | 静音清单季度复核；新增静音须写明理由与到期日 |
| 无法定位 | 告警必须带可执行命令（28.3） |
| 无闭环 | 告警关联偏差台账；关闭需记录处置 |

### 28.5 现状与差距

| 项 | 现状 | 差距 | 归属 |
|---|---|---|---|
| 日更告警 | 有（PushPlus 汇总） | 无级别概念、无命令建议 | 28.3 |
| 体检告警 | 有（`db-audit` 输出） | 无自动推送（靠人跑） | K3 |
| 静音机制 | 部分（豁免/停更清单已存在） | 未与告警分级打通 | K3 |
| 趋势观测 | **无** | 无基准记录 | 09 §14.7 |
| 告警留痕 | 部分（推送记录） | 无结构化台账 | 28.4 |

## 章 29 · 消费侧兼容与接口治理

### 29.1 兼容性承诺（对消费侧）

| 承诺项 | 内容 | 破坏条件 |
|---|---|---|
| 读侧 API | `read_code`/`read_range`/`list_codes`/`latest_date` 语义稳定 | 签名或返回语义变化 |
| 布局无关 | 消费侧无需感知 `by_year`/`single`/`by_code` | 要求消费侧判布局 |
| 日期口径 | `YYYYMMDD` 字符串（月频 `YYYYMM`） | 改格式 |
| 列名 | 已发布列名不改（新增列默认可空） | 改名/改类型 |
| 单位 | 库内口径不变（`vol` 手、`amount` 千元、`mv` 万元…，14 §23.3） | 改单位 = **不兼容事件** |
| 版本可查 | `db_version.json` 可读 | 移除 |

### 29.2 破坏性变更定义与流程

**破坏性变更**：改列名/类型/单位/日期格式/读侧 API 语义/删除表/改目录语义。

```
① 判定（是否破坏性）→ ② 记录 ADR 或变更单 → ③ 通知消费侧（含替代用法）
→ ④ 双写/兼容期（若可行）→ ⑤ 版本号 +1（minor 或 major）→ ⑥ 快照 + 文档更新
```

**纪律**：**静默改口径 = P0**（比数据错误更难发现，因为它看起来"一直是这样"）。

### 29.3 弃用与替换策略

| 场景 | 现行做法（先例） |
|---|---|
| 引擎/入口替换 | 旧入口保留为**隐藏别名**（CLI 收编 `leverage`/`etf-flow`/`gap-update`）→ 契约白名单依赖其存在（R1） |
| 废弃能力 | 调用即抛 `DeprecatedEngineError`（R7：**不得静默跑错**，如 `gap_update`/`intraday_update`） |
| 表替换 | 新表先建 + 并行验证期 + 消费侧切换 + 旧表标注弃用（不立即删） |

**原则**：**弃用要响**（显式抛错/告警），**删除要慢**（历史不可再生）。

### 29.4 多消费方版本协商

| 机制 | 内容 |
|---|---|
| 版本记录 | 消费侧结论/报告必须记 `db_version` + 各表 `date_max`（08 §13.7） |
| 兼容矩阵（建议） | 维护"读侧 API × 消费方"矩阵：谁在用、何时核对 |
| 变更影响面 | 改表前列出受影响消费侧清单（由表→消费者登记得出） |

### 29.5 现状与差距

| 差距 | 风险 | 建议 |
|---|---|---|
| 消费方清单未成文 | 改表时漏通知 | K1 字典增 `consumers` 字段 |
| 无兼容矩阵 | 破坏性变更发现晚 | §29.4 |
| 影子缓存未登记版本 | 结论不可复算 | 14 §23.5 |

## 章 30 · 迁移与演进工程

### 30.1 迁移类型

| 类型 | 例子 | 风险 |
|---|---|---|
| 布局迁移 | `by_code → by_year`（历史已做，`moneyflow` 提速 ≈40×） | 高（读者若判布局会读空） |
| 规格迁移 | 新增/改列、改判重主键 | 中（需 `schema_hash` 登记） |
| 源迁移 | 主源 → 备源替换（如 `share_float` → akshare） | 中（口径差异须验证） |
| 目录重组 | 停更表迁 `_stale/`（开放问题 O-5） | 低（但会破坏消费侧路径依赖，须先解耦） |

### 30.2 迁移六步法（写成通用流程）

```
① 冻结：迁移期间停写该表（记录冻结窗口）
② 备份：原文件保留（或快照），可回退
③ 迁移：脚本化（入 tools/，可重跑，幂等）
④ 守恒校验：rows_before − rows_after − dedup_removed == 0（≠0 即回滚）
⑤ 验证：db-audit（断点/重复/缺口/规模）+ 抽样比对（起点/终点/中间随机日）
⑥ 登记：文档字典 + db_version + 消费侧通知
```

**现状依据**：`tools/db_migrate.py` 已实现"守恒校验失败即回滚"，`moneyflow` 迁移为例（14 §22.1）。

### 30.3 迁移实测经验

| 经验 | 事实 |
|---|---|
| 按年大表收益显著 | `moneyflow` 迁移后 1 天/分 → 41 天/分（整年文件重写 ≫ 逐文件写） |
| 迁移期必须停写 | 否则守恒校验被并发写污染（→ PoC-5 写锁的动机之一） |
| 读者必须先具备布局无关性 | 否则迁移即"读空"事故（历史上已发生过） |
| 迁移脚本必须可重跑 | 迁移中失败需从中间态恢复；幂等设计是硬要求 |
| 迁移后必查起点 | `by_code` 表历史起点易被默认窗口截断（R13 教训） |

### 30.4 回滚方案

| 场景 | 回滚 |
|---|---|
| 迁移脚本失败（校验不过） | 自动回滚（原文件不动或从备份恢复） |
| 迁移后验收不通过 | 手工回滚（用快照/备份）；禁止"带着问题上线，日后再修" |
| 迁移后消费侧异常 | 优先回滚数据；若新布局本身正确，则修消费侧并记变更 |

### 30.5 迁移纪律与禁区

**纪律**：迁移必须脚本化（禁止手工 mv/改文件）、必须有守恒校验、必须停写、必须有回滚路径、必须登记。

**禁区**：① 无脚本的人工迁移 ② 迁移同时改口径 ③ 迁移后不跑 `db-audit` ④ 未通知消费侧就改布局语义。

## 章 31 · 反模式清单

> 每条给"症状 → 后果 → 正解"。全部来自本库**已发生过的真实事故**或明确风险（09 §14.2、11 §17）。

### 31.1 写侧反模式

| # | 症状 | 后果 | 正解 |
|---|---|---|---|
| A1 | 调用方自行拼接年度路径写文件 | 布局翻转 → 读空（静默） | 走 `table_storage_layout` + `LayoutGuardError`（ADR-5） |
| A2 | 用"更新元数据"掩盖成 dry-run | 真请求真覆盖写（`fund_basic` 事故） | dry-run 必须零副作用；R16 指纹断言 |
| A3 | 新建文件分支不做判重 | 首次建库固化重复行 | `_concat_pages` 全列去重 + 建库后必查重复 |
| A4 | 断点先记、落盘后做 | "以为有/其实没有" | 先落盘后记断点（INV-3） |
| A5 | 非原子写（直接写目标文件） | 半写文件破坏读数 | `tmp + os.replace` 原子写 |
| A6 | 迁移不校验行数守恒 | 静默丢行 | `rows_before − rows_after − dedup_removed == 0` 否则回滚 |
| A7 | 手工改文件/改断点 | 不可追溯 | 一律脚本化 + 留痕 |

### 31.2 消费侧反模式（INV-8 核心）

| # | 症状 | 后果 | 正解 |
|---|---|---|---|
| B1 | `glob(".../by_year/*/[0-9]*.parquet")` 反推标的/日期 | 布局一变全崩；易把目录名当年份 | 用 `reader` API；布局不可知（INV-8） |
| B2 | 依赖目录名/文件名语义（如"2026"目录=年份） | 迁移即失效 | 只依赖列（`trade_date`），不依赖路径 |
| B3 | 读出来顺手做单位换算（×100 / ÷10000）且不声明 | 隐性 100× / 1e4 误差 | 服务层显式换算一次并标注（14 §23.3） |
| B4 | 把空值当 0/把 0 当缺失 | 统计口径错 | 空/0/缺失三态分治（15 §27.4） |
| B5 | 假设"每表每天都有数据" | 停牌/停更表被当故障或误算 | 用日期集合与停更清单判断 |
| B6 | 默认 `how='left'` 跨库联查不查匹配率 | 匹配率 3.3% 却"有输出"（R14 实证） | 强制报匹配率，低于阈值告警 |
| B7 | 结论不记 `db_version`/`date_max` | 不可复算（08 §13.7） | 结论必带版本与截止日 |
| B8 | 消费侧写库（"顺手补一列"） | 污染主干、不可追溯 | 只读；派生写独立目录（INV-4/INV-7） |

### 31.3 运维与调度反模式

| # | 症状 | 后果 | 正解 |
|---|---|---|---|

### 31.4 测试与文档反模式
